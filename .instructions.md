# MDM Workflow Rules (Markdown-Driven Development)

You are operating in strict incremental sprint mode.

### Non-negotiable (agents working in this repo)

- **ALWAYS `git commit` validated work before ending your turn.** Every coherent slice—often down to a single file—gets its own commit once checks pass. **Never** leave the repo dirty because you were unsure whether committing was allowed; **never** wait for a separate “please commit” unless the user explicitly deferred commits for this session.
- **Never `git push` unless the user explicitly asks**—see *Push policy* below.
- If generic tooling defaults conflict with the above, **this document wins for LocalRecorder.**

## Primary Rules

1. All work must occur locally by default.
2. Do NOT configure git remotes unless explicitly directed by the user.
3. **ALWAYS commit locally after every single validated change** (rule above). Bump `package.json` per §8 when applicable; document per §5–§6 as appropriate. Do **not** accumulate unrelated uncommitted edits across turns unless the user explicitly tells you to hold commits.
4. Do NOT create cloud dependencies unless explicitly instructed.
5. Every sprint **and every discrete committed slice of work** must land as a stable **local commit** before you continue or idle out—not merely “eventually”.
6. Prefer small atomic changes over large refactors.
7. Preserve existing working functionality whenever possible.

### Push policy (on-demand only — current default)

- **Never push automatically:** No pushes after mini-sprints, FRs, feature branches, or idle-session wraps unless the user **explicitly** asks (e.g. “push”, “push this branch”, “publish to origin”). Treat push as **opt-in per request for now**.
- Before pushing when asked: confirm **remote** and **branch**, push **only** that branch (no `--all`), never `--force` / destructive pushes unless the user explicitly requests them.
- Never reconfigure remotes or default branches unless explicitly directed.
- Local commit + validations remain mandatory **before** any push.

Optional (human/agent judgement): after landing commits when relevant work feels “done”, you **may ask once** whether the user wants a push—you **must still wait for explicit approval** before pushing (`push` is **on demand**, never automatic).

# Sprint Workflow

For EVERY sprint execute the following sequence IN ORDER:

## (1) Sync & Inspect

Run:

- git fetch (if remotes exist)
- git pull (if remotes exist)
- git status

Then analyze:
- changed files
- untracked files
- merge conflicts
- repository health

Do NOT continue if repository state is unsafe.

---

## (2) Plan Sprint

Before coding:

- summarize sprint goal
- identify affected files
- identify possible risks
- define validation approach
- define rollback scope

Keep plans concise.

---

## (3) Implement

Perform ONLY the smallest useful implementation for the sprint.

Rules:
- avoid unrelated refactors
- avoid placeholder TODO logic
- avoid deleting large blocks unless necessary
- preserve backward compatibility when possible
- prefer explicit readable code

---

## (4) Validate

Run ALL lightweight validations possible.

Examples:
- unit tests
- linting
- syntax validation
- type checks
- markdown validation
- HTML validation
- script execution sanity checks

If tests fail:
- attempt repair
- document failures clearly

Do NOT falsely claim tests passed.

---

## (5) Documentation Update

After EVERY sprint:

Update:
- README.md
- sprint log markdown
- architecture notes if changed
- changelog if applicable

Documentation must include:
- what changed
- why it changed
- files modified
- known limitations
- next sprint ideas

---

## (6) HTML Mirror

Generate/update HTML documentation mirroring markdown docs.

Rules:
- preserve structure
- preserve headings
- preserve code blocks
- preserve hyperlinks
- use clean readable formatting
- avoid heavy frameworks unless requested

---

## (7) Review Changes

Before commit:
- summarize modified files
- summarize risks
- summarize validations run
- summarize remaining concerns

---

## (8) Bump Version

Before committing, increment `package.json` `"version"` using semantic versioning:

| Change type | Bump |
|---|---|
| Bug fix / patch (no new surface) | `0.x.Y → 0.x.Y+1` |
| New feature / minor addition | `0.X.0 → 0.X+1.0` |
| Breaking change or major milestone | `X.0.0 → X+1.0.0` |

Rules:
- Never skip this step — every commit must carry a unique version.
- The running server exposes its version at `GET /api/config` (`"version"` field).
- The UI renders the version in the sidebar header so the user can confirm a server restart picked up new code without needing to inspect files.

## (9) Commit Locally

Immediately after the validated change (rule 3), create a **small atomic commit**.

Commit message format:

[sprint-X] vX.Y.Z concise-description

Examples:
- [sprint-1] v0.1.0 initialize local recorder pipeline
- [sprint-2] v0.1.1 fix chunked whisper transcription ordering
- [sprint-3] v0.2.0 add local web UI

Do **not** push unless the user explicitly requests it (*Push policy* above).

---

## (10) Push to origin

**Only when the user explicitly asks.** Run `git push` or `git push -u origin <branch>` as appropriate—never as an automatic follow-up to steps (2)–(9).

Same safeguards as *Push policy*: confirm branch/remote, no `--all`, no force-push unless explicitly requested.

# Development Philosophy

Prefer:
- maintainability
- observability
- rollback safety
- incremental progress
- documentation-first thinking

Avoid:
- giant rewrites
- hidden magic
- unnecessary abstractions
- premature optimization
- excessive dependencies

The project is a local-first AI memory and workflow assistant.

Core capabilities may include:
- local audio recording
- chunked transcription
- local summarization
- heat/trend analysis
- markdown knowledge persistence
- searchable memory
- periodic summaries
- low-power idle listening

All architecture decisions should support:
- privacy
- offline operation
- incremental scalability
- local GPU acceleration
- human reviewability
