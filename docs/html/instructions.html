MDM Workflow Rules (Markdown-Driven Development)

You are operating in strict incremental sprint mode.

Primary Rules

  1. All work must occur locally by default.
  2. Do NOT configure git remotes unless explicitly directed by the user.
  3. Do NOT push to origin unless explicitly directed by the user. When directed, push only the active branch and only after the sprint's local commit has been validated.
  4. Do NOT create cloud dependencies unless explicitly instructed.
  5. Every sprint must end in a stable local commit, regardless of whether a push is also performed.
  6. Prefer small atomic changes over large refactors.
  7. Preserve existing working functionality whenever possible.

As-Directed Pushes

When the user explicitly authorizes pushing:

  • Confirm the target remote and branch before pushing.
  • Push only the active branch (no --all, no force pushes).
  • Never reconfigure existing remotes or change default branches without explicit direction.
  • Treat each authorization as scoped to the current sprint unless the user says otherwise.
  • Local commit and validation steps remain mandatory before any push.

Sprint Workflow

For EVERY sprint execute the following sequence IN ORDER:

(1) Sync & Inspect

Run:

  • git fetch (if remotes exist)
  • git pull (if remotes exist)
  • git status

Then analyze:

  • changed files
  • untracked files
  • merge conflicts
  • repository health

Do NOT continue if repository state is unsafe.

(2) Plan Sprint

Before coding:

  • summarize sprint goal
  • identify affected files
  • identify possible risks
  • define validation approach
  • define rollback scope

Keep plans concise.

(3) Implement

Perform ONLY the smallest useful implementation for the sprint.

Rules:

  • avoid unrelated refactors
  • avoid placeholder TODO logic
  • avoid deleting large blocks unless necessary
  • preserve backward compatibility when possible
  • prefer explicit readable code

(4) Validate

Run ALL lightweight validations possible.

Examples:

  • unit tests
  • linting
  • syntax validation
  • type checks
  • markdown validation
  • HTML validation
  • script execution sanity checks

If tests fail:

  • attempt repair
  • document failures clearly

Do NOT falsely claim tests passed.

(5) Documentation Update

After EVERY sprint:

Update:

  • README.md
  • sprint log markdown
  • architecture notes if changed
  • changelog if applicable

Documentation must include:

  • what changed
  • why it changed
  • files modified
  • known limitations
  • next sprint ideas

(6) HTML Mirror

Generate/update HTML documentation mirroring markdown docs.

Rules:

  • preserve structure
  • preserve headings
  • preserve code blocks
  • preserve hyperlinks
  • use clean readable formatting
  • avoid heavy frameworks unless requested

(7) Review Changes

Before commit:

  • summarize modified files
  • summarize risks
  • summarize validations run
  • summarize remaining concerns

(8) Commit Locally

Create a small atomic commit.

Commit message format:

[sprint-X] concise-description

Examples:

  • [sprint-1] initialize local recorder pipeline
  • [sprint-2] add chunked whisper transcription
  • [sprint-3] add rolling markdown summaries

Do NOT push by default. Only push when explicitly directed by the user per the As-Directed Pushes rule above.

Development Philosophy

Prefer:

  • maintainability
  • observability
  • rollback safety
  • incremental progress
  • documentation-first thinking

Avoid:

  • giant rewrites
  • hidden magic
  • unnecessary abstractions
  • premature optimization
  • excessive dependencies

Project Goals

The project is a local-first AI memory and workflow assistant.

Core capabilities may include:

  • local audio recording
  • chunked transcription
  • local summarization
  • heat/trend analysis
  • markdown knowledge persistence
  • searchable memory
  • periodic summaries
  • low-power idle listening

All architecture decisions should support:

  • privacy
  • offline operation
  • incremental scalability
  • local GPU acceleration
  • human reviewability
