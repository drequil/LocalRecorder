MDM Workflow Rules (Markdown-Driven Development)

You are operating in strict incremental sprint mode.

Primary Rules

  1. All work must occur locally by default.
  2. Do NOT configure git remotes unless explicitly directed by the user.
  3. Commit and remote sync: When you complete a mini-sprint, a feature request (FR) deliverable, or a feature-branch (FB) scoped change, you must end with a local commit (after validation, version bump when applicable, and docs) and git push of the active branch to origin so shared state stays current—unless the user has asked to keep work local-only for this session or repo. For informal one-offs outside those scopes, commit when done but push only when the user explicitly directs (see As-Directed Pushes for edge cases).
  4. Do NOT create cloud dependencies unless explicitly instructed.
  5. Every sprint must end in a stable local commit, regardless of whether a push is also performed.
  6. Prefer small atomic changes over large refactors.
  7. Preserve existing working functionality whenever possible.

As-Directed Pushes

When pushes are not already required by rule 3 above (e.g. ad-hoc edits, hotfixes, or the user has opted out of automatic pushes), push only when the user explicitly directs. Before pushing:

  • Confirm the target remote and branch before pushing.
  • Push only the active branch (no --all, no force pushes).
  • Never reconfigure existing remotes or change default branches without explicit direction.
  • Treat each authorization as scoped to the current task unless the user says otherwise.
  • Local commit and validation steps remain mandatory before any push.

Sprint Workflow

For EVERY sprint execute the following sequence IN ORDER:

(1) Sync & Inspect

Run:

  • git fetch (if remotes exist)
  • git pull (if remotes exist)
  • git status

Then analyze:

  • changed files
  • untracked files
  • merge conflicts
  • repository health

Do NOT continue if repository state is unsafe.

(2) Plan Sprint

Before coding:

  • summarize sprint goal
  • identify affected files
  • identify possible risks
  • define validation approach
  • define rollback scope

Keep plans concise.

(3) Implement

Perform ONLY the smallest useful implementation for the sprint.

Rules:

  • avoid unrelated refactors
  • avoid placeholder TODO logic
  • avoid deleting large blocks unless necessary
  • preserve backward compatibility when possible
  • prefer explicit readable code

(4) Validate

Run ALL lightweight validations possible.

Examples:

  • unit tests
  • linting
  • syntax validation
  • type checks
  • markdown validation
  • HTML validation
  • script execution sanity checks

If tests fail:

  • attempt repair
  • document failures clearly

Do NOT falsely claim tests passed.

(5) Documentation Update

After EVERY sprint:

Update:

  • README.md
  • sprint log markdown
  • architecture notes if changed
  • changelog if applicable

Documentation must include:

  • what changed
  • why it changed
  • files modified
  • known limitations
  • next sprint ideas

(6) HTML Mirror

Generate/update HTML documentation mirroring markdown docs.

Rules:

  • preserve structure
  • preserve headings
  • preserve code blocks
  • preserve hyperlinks
  • use clean readable formatting
  • avoid heavy frameworks unless requested

(7) Review Changes

Before commit:

  • summarize modified files
  • summarize risks
  • summarize validations run
  • summarize remaining concerns

(8) Bump Version

Before committing, increment package.json "version" using semantic versioning:

Change type Bump
Bug fix / patch (no new surface) 0.x.Y → 0.x.Y+1
New feature / minor addition 0.X.0 → 0.X+1.0
Breaking change or major milestone X.0.0 → X+1.0.0

Rules:

  • Never skip this step — every commit must carry a unique version.
  • The running server exposes its version at GET /api/config ("version" field).
  • The UI renders the version in the sidebar header so the user can confirm a server restart picked up new code without needing to inspect files.
  • Update this table example row after each bump so the history is traceable.

(9) Commit Locally

Create a small atomic commit.

Commit message format:

[sprint-X] vX.Y.Z concise-description

Examples:

  • [sprint-1] v0.1.0 initialize local recorder pipeline
  • [sprint-2] v0.1.1 fix chunked whisper transcription ordering
  • [sprint-3] v0.2.0 add local web UI

Do NOT push by default for non-sprint / non-FR / non-FB edits unless the user directs. For sprint / FR / FB work, rule 3 already requires push unless opted out.

(10) Push to origin

If rule 3 applies (mini-sprint, FR, or FB change committed in step 9):

  • Run git push (or git push -u origin <branch> on first publish for that branch) after the commit.
  • Do not force-push or --all unless the user explicitly asks.

If rule 3 does not apply, push only when the user directs (As-Directed Pushes).

Development Philosophy

Prefer:

  • maintainability
  • observability
  • rollback safety
  • incremental progress
  • documentation-first thinking

Avoid:

  • giant rewrites
  • hidden magic
  • unnecessary abstractions
  • premature optimization
  • excessive dependencies

Project Goals

The project is a local-first AI memory and workflow assistant.

Core capabilities may include:

  • local audio recording
  • chunked transcription
  • local summarization
  • heat/trend analysis
  • markdown knowledge persistence
  • searchable memory
  • periodic summaries
  • low-power idle listening

All architecture decisions should support:

  • privacy
  • offline operation
  • incremental scalability
  • local GPU acceleration
  • human reviewability
